# 未来升级方向与规划

本文档说明项目下一步可以往哪走，以及**为什么有的方向目前不做**。

排序依据是：**投入产出比 × 与现有架构的契合度**。

---

## 判断标准

每提一个功能，先过三个问题：

1. **它能不能减少一次"记不住"？** —— 这是项目的根本目标
2. **它能不能用现有架构实现？** —— 避免为了一个功能引入服务器/构建链
3. **它是不是"通用产品做不好、只有自己家做得好"的事？** —— 这是本项目的差异化价值

三个问题有一个答"不能"，就要慎重。

---

## 一、近期（低成本，明确有价值）

这几个都是小改动，不引入新依赖。

### 1.1 PWA 化 + 主屏图标

**现状**：手机浏览器打开能用，但每次要找链接。

**方案**：加 `manifest.json` + 简单的 Service Worker。

```json
{
  "name": "家庭维护台",
  "short_name": "维护台",
  "start_url": "./index.html",
  "display": "standalone",
  "background_color": "#ffffff",
  "theme_color": "#2c6e4f",
  "icons": [
    { "src": "icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "icon-512.png", "sizes": "512x512", "type": "image/png" }
  ]
}
```

Service Worker 只需要做两件事：缓存页面本身 + 缓存最近一次的数据快照。

**收益**：

| 项 | 提升 |
|---|---|
| 启动 | 从"找链接"变成"点图标" |
| 离线 | 断网也能看缓存的数据 |
| 体验 | 全屏无地址栏，接近原生 App |

**成本**：约半天。两个文件 + 页面加几行注册代码。

**风险**：低。Service Worker 缓存策略配错会导致页面不更新，用"网络优先 + 缓存兜底"即可避免。

---

### 1.2 最低库存告警

**现状**：只有当"备件库存 = 0"时才进采购清单。

**问题**：耗材到货有周期，等到 0 再买就断供了。比如滤芯要网购，3 天才能到。

**方案**：借鉴 Grocy 的做法，为每种耗材设"安全库存线"。

在「维护清单」表加一个字段：

| 字段名 | 类型 | 说明 |
|---|---|---|
| 安全库存 | 数字 | 低于此值就提醒，默认 0 |

判断逻辑改成：

```js
// 现在：只有 0 才告警
if (stock === 0) → 需购买

// 改后：低于安全线就告警
if (stock <= safeStock) → 需购买（标注"已低线"）
```

**为什么借鉴 Grocy**：它是这个领域最成熟的开源方案，安全库存是它的标准配置，验证过有效。

**成本**：约 2 小时。加字段 + 改判断 + 页面上标个橙色小点。

---

### 1.3 多成员消息推送

**现状**：所有提醒都是"打开页面才看到"。

**问题**：这其实是当前最大的功能缺口。如果家人不主动打开页面，什么提醒都送不到。

**方案**：接入企业微信 / 钉钉机器人。

```
云端巡检任务
    │
    ├─ 有需要通知的事（如"今天该换滤网"）
    │
    ▼
POST 机器人 webhook
    │
    ▼
家庭群收到消息
```

实现很简单——就是在巡检规则的第 5 步（收尾）加一条："如果有需要通知的事项，调用 webhook 发送"。

**收益**：从"被动查看"变成"主动触达"。**这是质变**。

**成本**：约半天。建群机器人 + 在规则里加一步。

**要注意的**：

| 问题 | 处理 |
|---|---|
| 消息刷屏 | 加频控：同类事项每天最多推一次 |
| 隐私 | webhook 地址是敏感信息，存在数据表里不要提交到仓库 |
| 推送失败 | 不能因为推送失败就判定整个任务失败 |

---

### 1.4 位置层级化

**现状**：「存放位置」是单层——"客厅""厨房""客卫"。

**问题**：东西多了之后，"客卫"里到底在哪个柜子、哪一层，还是找不到。

**方案**：借鉴 HomeBox 的三级模型：

```
房间（客厅）
  └── 家具/柜子（电视柜）
        └── 层板/抽屉（第二层）
```

对应的「存放位置」表改成自引用结构：

| 字段名 | 类型 | 说明 |
|---|---|---|
| 名称 | 文本 | 如"电视柜" |
| 层级 | 单选 | 房间 / 柜子 / 层板 |
| 上级位置 | 文本 | 指向父级名称 |

页面上显示路径：`客厅 > 电视柜 > 第二层`。

**为什么借鉴 HomeBox**：这是它做得最扎实的部分，也是仓库管理类应用的核心。

**成本**：约 1 天。主要工作量在页面上的路径选择和面包屑导航。

**注意**：如果家里东西不多，这个方向收益有限。**建议等物品归档表超过 50 条再考虑。**

## 二、中期（需要额外开发量）

### 2.1 扫码录入

**方案**：给物品贴二维码（一张 A4 纸打印一堆），扫码直达详情页。

```
二维码内容：https://<页面地址>?item=<recordId>
```

页面启动时解析 `item` 参数，直接打开对应物品的详情弹层。

**收益场景**：

- 新买的耗材扫码入库
- 找东西时扫柜子上的码，看里面有什么
- 盘点时挨个扫一遍

**技术上可行的原因**：页面是单文件的，加一个 URL 参数解析即可，不需要后端。

**成本**：约 2 天。URL 参数路由 + 详情页直达 + 二维码生成工具。

**为什么值得做**：HomeBox 已经验证过这个交互——**扫码是"录入"这件事的最优解**，比打开 App 再翻菜单快得多。

---

### 2.2 米家 / Home Assistant 接入

**现状**：所有维护周期都是"按天数估算"。

**问题**：估算不准。比如新风机滤网，说明书说 180 天，但如果你家空气质量好、开机少，实际能用 300 天；反之可能 120 天就该换。

**方案**：如果设备能上报状态，就能从"按周期估算"升级为"按实际使用量计算"。

```
现在是：上次更换日期 + 180 天 = 该换了
理想是：累计运行小时数 / 额定寿命 = 剩余百分比
```

**状态**：⚠️ **目前搁置**。原因是平台暂未开放米家接入，相关自动化已暂停。

**重启的触发条件**：

- 平台支持接入米家
- 或者设备本身有开放 API（部分品牌的 App 可以导出使用数据）

**如果重启，实现路径**：

| 方案 | 说明 | 难度 |
|---|---|---|
| A. 直接调米家 API | 需要米家开发者账号 | 中 |
| B. 走 Home Assistant | HA 有统一接口，但需要自建 | 高 |
| C. 手工月更 | 每月手动填一次设备使用数据 | 低（但没解决问题） |

**提醒**：这个方向不是"越早做越好"。**在设备不支持上报之前，强行做只是增加维护负担。**

---

### 2.3 数据可视化

**方案**：加一个"统计"页。

| 图表 | 数据来源 | 价值 |
|---|---|---|
| 家庭支出趋势（月度/年度） | 家庭账本 + 固定费用 | 看得见钱花在哪 |
| 维护频次热力图 | 维护日志 | 哪些设备最费心 |
| 耗材消耗速度曲线 | 维护日志 + 库存变化 | 修正"经验消耗天数"的估算 |
| 库存周转 | 日用品库存 | 囤货是否过量 |

**成本**：约 2 天。需要引入一个轻量图表库（约 30 KB）或用原生 Canvas 手写简单图表。

**权衡**：引入图表库会打破"零依赖"现状。如果要保持零依赖，图表就得手写——复杂图表手写成本高。

**建议**：先做最简单的（纯 CSS 的条形图），够用就行。

---

### 2.4 多家庭 / 多房产支持

**现状**：一套表对应一套房子。

**问题**：如果同时管理父母家，或者有第二套房，数据会混在一起。

**方案**：加"房产"维度。所有表的记录都带一个"所属房产"字段，页面顶部加房产切换器。

**成本**：改动面较大——所有表加字段、所有查询加过滤、所有渲染加维度。

**建议**：**除非真的有两套房需要管，否则不做。** 这个改动会让代码复杂度显著上升，而收益场景很窄。

---

## 三、远期（方向性探索）

### 3.1 图片识别录入

**场景**：拍一张耗材包装，自动识别型号、规格、建议更换周期，自动填表。

**技术路径**：

```
拍照 → OCR 识别文字 → 提取型号/规格 → 匹配已有设备 → 预填表单
```

**现状**：已在研究 Tesseract OCR 的本地识别方案。

**难点**：

| 难点 | 说明 |
|---|---|
| 包装文字排版乱 | 型号、规格、厂家信息位置不固定 |
| 需要本地跑 | 涉及隐私，不适合传云端 |
| 准确率 | 识别错了比不识别更麻烦 |

**建议**：作为"辅助填表"而非"全自动"。识别结果预填到表单里，人工确认后再保存。

---

### 3.2 语音录入

**场景**：做完维护，说一句"洗衣机筒清洁做完了"，直接落库。

**技术路径**：浏览器的 Web Speech API 已经有了，但中文识别质量和对家居语境的适应是问题。

**为什么优先级低**：**这个场景的收益不大**。做完维护点一下按钮（"已更换"）只需要 2 秒，语音录入省不了多少，还要处理识别错误。

**除非**：手上有水、有油的时候不方便点屏幕——这个场景确实存在，但足够高频吗？存疑。

---

### 3.3 自托管版本

**方案**：把数据层从云数据库换成 SQLite / Postgres，整套跑在自己的 NAS 上。

**架构变化**：

```
现在：
  浏览器 ──SDK──▶ 云数据库

自托管：
  浏览器 ──HTTP──▶ 自建后端（Node/Python）──▶ SQLite
```

**好消息**：页面的 SDK 接口契约很薄——只有 8 个方法（`query` / `getSchema` / `getRecord` / `addRecord` / `updateRecord` / `deleteRecord` / `uploadImage` / `onUpdated`）。**只要实现这 8 个方法，页面代码一行都不用改。**

`demo/mock4.js` 就是约 150 行的参考实现。

**收益**：

| 收益 | 说明 |
|---|---|
| 数据主权 | 数据完全在自己手里 |
| 摆脱平台依赖 | 平台改政策也不怕 |
| 无限扩展 | 可以加任何想加的功能 |

**成本**：

| 成本 | 说明 |
|---|---|
| 开发 | 约 1-2 周（后端 + 认证 + 部署脚本） |
| **运维** | **这是真正的问题** |
| 内网穿透 | 出门在外怎么访问家里的服务 |
| 备份 | 自己要保证不丢数据 |
| 升级 | 自己要维护整个技术栈 |

**⚠️ 当前不迁移的理由**：

> 一个家庭应用，如果维护它本身变成了新的家务，那它就失败了。

现在这个形态——**没有服务器要守护、没有进程要重启、没有依赖要升级**——正是它最大的优点。为了"数据主权"而引入一台需要维护的服务器，在当前的规模下是**净亏损**。

**触发条件**（满足任一再考虑）：

1. 平台依赖成为实际障碍（如接口变更导致页面失效）
2. 数据敏感度上升到不能放云端
3. 需要平台不支持的底层能力
4. 家里已有正在运行的 NAS，且你不介意多维护一个服务

**在这些条件满足之前，自托管是"为了架构洁癖付出的运维代价"。**

## 四、明确不做的事

有些方向看起来合理，但**想清楚之后决定不做**。

### ❌ 做成通用 SaaS

**为什么不**：

这个项目的价值恰恰在于它是**为自己家定制的**。

| 通用的部分 | 定制的部分 |
|---|---|
| 剩余天数计算 | 房间里到底有哪几个房间 |
| 库存判断 | 家里到底有哪些设备 |
| 费用滚动 | 家人的习惯和偏好 |

**恰恰是"定制的部分"决定了它好不好用**，而这部分通用产品做不好——因为它不知道你家有什么。

一旦开始追求通用性，就要开始做配置界面、做兼容、做文档、做支持。**那就变成了另一个待办 App**，而这个赛道已经很拥挤了。

**正确的用法**：你把这个项目 fork 走，改成适合你自己家的版本。**这才是它最好的归宿。**

---

### ❌ 堆砌功能

每加一个功能，先问：

> 它是不是真的能减少一次"记不住"？

如果答案是"这个功能挺酷的"，那就不加。

**已经拒绝过的例子**：

| 想法 | 拒绝理由 |
|---|---|
| 家庭聊天 | 有微信群了 |
| 记账预算分析 | 记账 App 更专业，这里只记流水就够 |
| 智能家居控制 | 米家 App 更专业 |
| 家庭日历/日程 | 手机自带日历更专业 |
| 社交分享 | 家庭事务不需要社交 |

**边界很清楚**：只做"**设备维护 + 消耗品 + 周期性事务**"这一件事。

---

### ❌ 追求技术现代化

不引入框架、不引入构建链、不拆分成多个文件。

**理由**：

| 保持现状的好处 | 说明 |
|---|---|
| 部署 = 上传一个文件 | 没有构建，没有依赖安装 |
| 不会有依赖漏洞 | 没有依赖 |
| 五年后还能跑 | 不依赖 npm 生态的稳定性 |
| 任何人都能改 | 打开记事本就能改 |

**对个人项目来说，"简单到不需要思考"比"技术上先进"重要得多。**

---

## 五、优先级建议

如果只能做三件事，按这个顺序：

| 优先 | 事项 | 理由 |
|---|---|---|
| 🥇 | **多成员消息推送** | 补上最大的功能缺口（主动触达） |
| 🥈 | **PWA 化** | 投入最小（半天），体验提升最直接 |
| 🥉 | **最低库存告警** | 解决真实的断供问题 |

其余方向，**在有实际需求驱动之前，先不做**。

## 六、一个反直觉的观察

这个项目迭代到现在，一个反复出现的规律是：

> **最好的改进往往来自"用的时候被卡住"，而不是"想的时候觉得应该做"。**

举几个真实的例子：

| 改进 | 起因 |
|---|---|
| 表单默认值不再覆盖用户输入 | 给猫记录护理，两条记录都变成了同一只猫 |
| 加载失败要显示"未加载"而不是"没有记录" | 表增加到 16 张时被限流，界面全空，以为数据丢了 |
| 门控用时间差而不是周一 | 被问"改成 1 小时一次岂不是周一跑 24 次" |
| 链接必须过 `docLink()` | 说明书链接渲染成了 `[object Object]` |
| 读表要限定范围 | 一次整表读 7.7 万字符，导致任务连续失败 |

**没有一条是"规划"出来的，全是踩出来的。**

所以对路线图的正确用法不是"照着做"，而是：**用它做参考，但真正的方向由使用中的痛感决定。**

---

## 七、给 fork 的人的建议

如果你打算基于这个项目做自己的版本，建议：

1. **先跑通离线演示**，理解交互模型（`demo/demo5.html`）
2. **再读 `docs/项目结构说明.md`**，理解代码组织
3. **然后只建你需要的那几张表**，不要一次建 17 张
4. **用两三个月**，让"痛感"告诉你该加什么
5. **最后才考虑加 AI 任务**，因为它是可选的高级功能

**最容易走的弯路**：一上来就把 17 张表全建好、AI 任务全配上，结果发现大部分功能自己根本用不上，反而增加了维护负担。

**记住**：这个项目的第一原则是**"可变的东西放数据表"**，第二原则是**"不为假设的需求写代码"**。
