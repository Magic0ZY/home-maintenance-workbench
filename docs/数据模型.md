## 1. 维护清单

**核心表**。页面上"维护"页的全部内容、以及 AI 的采购判断，都基于它。

| 字段名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| 维护项 | 文本 | ✅ | 如"尘袋""中效滤网" |
| 所属设备 | 文本 | ✅ | 如"扫地机器人" |
| 房间 | **单选** | | ⚠️ 页面房间下拉的唯一来源 |
| 类别 | 单选 | | 米家电器 / 宠物设备 / 清洁设备 / 厨房电器 / 卫浴电器 / 其他 |
| 维护动作 | 单选 | | 清洗 / 更换滤网 / 更换耗材 / 更换电池 / 深度保养 / 其他 |
| 周期天数 | 数字 | ✅ | 建议更换周期 |
| 上次维护日期 | 日期 | ✅ | 剩余天数的计算基准 |
| 耗材型号 | 文本 | | 用于生成购物搜索链接 |
| 备件库存 | 数字 | | 决定是否进采购清单 |
| 耗材单价 | **货币** | | 采购清单估算 |
| 说明书链接 | **URL** | | ⚠️ 只填核实过的真实链接 |
| 说明书图片 | **图片** | | 说明书照片存档 |
| 负责人 | 文本 | | 谁负责这项维护 |
| 归属模块 | 单选 | | 家电 / 宠物 / 其他 —— 决定它出现在哪个面板 |
| 宠物 | 文本 | | 归属到哪只宠物（宠物模块用） |
| 备注 | 文本 | | 也用于写状态标记 |

### 计算逻辑

```
剩余天数 = (上次维护日期 + 周期天数) - 今天

分档：
  剩余 ≤ 0      → 逾期（红）
  1 ≤ 剩余 ≤ 7  → 快到期（橙）
  8 ≤ 剩余 ≤ 14 → 临近（黄）
  剩余 > 14     → 正常

采购判断：
  剩余 ≤ 0 且 备件库存 = 0  → 需购买
  剩余 ≤ 0 且 备件库存 > 0  → 无需购买（已有备件）
```

### ⚠️ 建房：房间字段是唯一来源

页面的房间下拉框**不硬编码任何房间名**，全部从这个字段的 `options` 读：

```js
db.getSchema({ databaseId: DB.MAINT }).then(function (schema) {
  (schema.properties || []).forEach(function (f) {
    if ((f.type === 'select' || f.type === 'multi_select') && f.config && f.config.options) {
      MAINT_OPTS[f.name] = f.config.options.map(function (o) { return o.text; });
    }
  });
});
```

**好处**：增删房间只需要改这个字段的选项。

**⚠️ 危险**：一旦这个字段有数据，**删掉某个选项会静默清空**引用它的单元格。所以选项要一次性想清楚。

### ⚠️ 备注字段兼作状态标记

AI 生成节日行程后，会在备注里写：

```
行程已生成 2026-09-21
```

下一轮读到这行字就跳过。**这是"状态落到数据里"原则的具体应用**——因为 AI 每次运行是无状态的，不能靠"记忆"来防重复。

**如果你想手工重置**：把备注里这行字删掉，AI 下一轮就会重新生成。

### 生日祝福的双数据源

页面顶部的生日横幅**同时查两个地方**：

1. 「家庭成员」表的 `生日` 字段
2. 「节日与生日」表中 `类型 = 生日` 的记录

用 `MM-DD` 匹配（忽略年份）。这样无论你在哪张表里记生日，都能提醒到。

### 状态是手工填的

注意：「状态」字段**不是自动算的**，是用户手工报备的。

为什么不做自动计算？因为囤货消耗速度太不规律（洗衣液夏天用得快、猫砂看猫的心情），自动推算反而不准。**让用户报备更可靠。**

`经验消耗天数` 是参考值，用于 AI 估算购买时机，不用于强制判断。

## 6. 任务请求表

**AI 任务信箱**。用户在页面「AI」页写的任务，都落到这张表。

| 字段名 | 类型 | 说明 |
|---|---|---|
| 任务类型 | 文本 | 如"采购清单生成""新增维护项" |
| 参数 | 文本 | 附加参数（如设备名） |
| 状态 | 单选 | **待执行** / 已完成 / 失败 |
| 提交时间 | 日期时间 | |
| 完成时间 | 日期时间 | |
| 提交人 | 文本 | |
| 已读 | 单选 | 未读 / 已读 |
| 结果 | 多行文本 | AI 的返回内容 |

### 状态流转

```
用户提交 → 待执行
              │
      AI 巡检读取
              │
      ┌───────┴───────┐
      ▼               ▼
   已完成           失败
  （写结果）      （写错误信息）
```

### 门控依赖这个表

AI 的第 0 步会读 `状态 = 待执行` 的条数。为 0 且距上次运行不足 7 天，就直接退出。

> ⚠️ **注意**：如果任务卡在"待执行"状态（AI 处理失败了），门控会一直认为"有事"，导致每轮都全量跑。所以**要定期检查有没有僵死的任务**。

## 7. AI任务注册表

**只有 1~3 条记录**。存规则全文和门控状态。

| 字段名 | 类型 | 说明 |
|---|---|---|
| 指令全文 | **多行文本** | 完整巡检规则（约 7,600 字符） |
| 上次运行 | 日期时间 | 门控判断依据 |
| 待执行数 | 数字 | 门控判断依据（冗余，方便快速读） |

### 为什么规则存这里

云端任务输入框上限约 **1,455 字符**，超出会**静默截断**。而完整规则约 7,600 字符。

所以把规则存进数据表，任务里只放一段约 1,200 字符的元提示词：

```
读取「AI任务注册表」中指令全文字段，按其中的规则执行本轮巡检。
```

**好处**：改规则只改数据，不用动任务配置。

### ⚠️ 读这张表要小心

`指令全文` 是长文本字段（7,600 字符）。门控阶段**不要读它**——那会让每轮都付出完整规则的读取成本。

正确做法：门控只读 `上次运行` 和 `待执行数` 两个短字段。**门控通过之后**才读 `指令全文`。

## 12. 数据快照

**全量备份表**。风险最高的一张表，因为它是唯一会存长文本的。

| 字段名 | 类型 | 说明 |
|---|---|---|
| 快照时间 | 日期时间 | |
| 表名 | 文本 | |
| 数据 | **多行文本（JSON）** | ⚠️ 会长得很大 |
| 条数 | 数字 | |

### 🚨 最关键的性能警告

> **一次把这张表整表读回来，会直接导致云端任务失败。**

**实际事故**：这张表累积到 **7.7 万字符**时，一次整表读取让连续两轮定时巡检（00:00 和 06:00）都失败。

**规则**：

```
✅ 只读"快照时间"字段做判断
✅ 只取最近一条
❌ 整表读取
❌ 为了"确认"重复读
```

**另外**：页面的 `pruneSnaps()` 只保留最近 N 条快照。**但加新表时必须同步更新 `SNAP_NAMES` 名单**，否则新表不会被备份。

### ⚠️ 这里踩过一个重要的坑

**表单的默认值不能覆盖用户已填的内容。**

**实际事故**：给两只宠物各新增一条护理记录（一条选宠物 A、一条选宠物 B），结果**两条都变成了宠物 A**，而且用户选的日期也被改成了今天。

原因：新增时无条件套用默认值。

```js
// ❌ 错误：无条件覆盖
if (!id && cfg.defaults) {
  for (var k in cfg.defaults) props[k] = cfg.defaults[k];
}

// ✅ 正确：只补空
var dft = cfg.defaults && cfg.defaults();
if (dft) {
  for (var k in dft) {
    if (!props[k]) props[k] = dft[k];
  }
}
```

**推广原则**：任何默认值逻辑都必须遵守"**只补空，不覆盖**"。

### 另一个教训：周期天数要符合实际

**"谁家猫洗澡周期是 30-90 天啊？"**

我最初按宠物店的美容标准，给猫设了 30-90 天的洗澡周期。**这是错的**——室内猫通常按需洗（一年一次甚至更少都正常），狗才需要那个频率。

**教训**：默认值不要照搬行业通用标准，要符合具体场景。现在 `360` 天是更合理的默认值。

### ⚠️ 设备档案的重大作用

**维护清单的"所属设备"必须先在这里存在，AI 才会接受。**

如果没有建档，AI 会报"**未建档**"，而不是自己新建一条。

**为什么这么设计**：防止 AI 乱建设备导致脏数据。**这是"AI 不许猜"原则的体现**。

**踩过的坑**：用户说"我买了个 XX 洗地机"，AI 在维护清单里加了一条，但设备档案里没有"XX"这个设备，页面显示"未建档"。

修复涉及三处：

1. 数据：补建该设备档案
2. 提示词：加"路由 ⓪"——新增维护项前先检查设备是否已建档
3. 页面：表单预填 + 显示"未建档"清单

## 字段值格式对照表

**这是最容易踩坑的地方**，单独列出来。

### 写入格式

```js
{
  // 文本
  '维护项': { text: '尘袋' },

  // 数字
  '周期天数': { number: 60 },

  // 货币
  '耗材单价': { currency: 39 },

  // 日期（必须是 YYYY-MM-DD）
  '上次维护日期': { date: '2026-09-01' },

  // 日期时间
  '提交时间': { date: '2026-09-17T15:52:00Z' },

  // 单选（值必须在 options 里）
  '房间': { select: '客厅' },

  // 多选（数组）
  '标签': { multi_select: ['耗材', '高频'] },

  // URL
  '说明书链接': { url: [{ link: 'https://...', text: '说明书' }] },
}
```

> ⚠️ **日期时间写北京时间**。平台按写入的字面值回读，不做位移。

### 读取格式

| 字段类型 | API 回传形态 | 处理函数 |
|---|---|---|
| 文本 | 字符串 | 直接用 |
| 单选 | 字符串 | 直接用 |
| **多选** | **数组** | 元素可能是对象，取 `.text` |
| 数字 | 数字 或 `{amount}` | `numOf()` |
| 货币 | 数字 或 `{amount}` | `numOf()` |
| 日期 | `'2026-09-17T00:00:00Z'` | `parseDay()` |
| **URL** | **数组** `[{link, text}]` | `docLink()` |
| **图片** | **数组** `[{imageUrl}]` | `imgUrlOf()` |
| 勾选 | 布尔 | 直接判断 |

### 🚨 最重要的一条

```js
// ❌ 错误：直接拼接
'<a href="' + rec['说明书链接'] + '">说明书</a>'
// 结果渲染成：[object Object]
// 浏览器按相对路径解析 → 打开报 NoSuchKey

// ✅ 正确：过转换函数
'<a href="' + esc(docLink(rec['说明书链接'])) + '">说明书</a>'
```

**URL、图片、多选字段都是数组**。这是本项目最危险的一个坑，**每一次渲染链接都必须过 `docLink()`**。
