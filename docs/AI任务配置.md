# AI 任务配置

本文档说明如何配置云端 AI 巡检。**不使用 AI 功能的话，本文可以跳过。**

---

## 一、为什么需要 AI

页面本身能处理所有**确定性判断**：

- 剩余天数够不够 → 算得出来
- 库存是不是 0 → 看得出
- 费用到期没 → 比得了

但有类事情页面做不了：

| 场景 | 为什么需要 AI |
|---|---|
| "我买了个洗地机，加进维护清单" | 自然语言 → 结构化数据 |
| "中秋节该准备什么" | 需要结合节日性质推荐事项 |
| "这周要买什么" | 需要跨表汇总 + 判断哪些真该买 |
| "说明书链接帮我找一下" | 需要理解设备 + 检索 |

**AI 在这里的定位是"队列执行器"**：你写任务 → 它读表 → 按规则执行 → 写回结果。不是聊天助手，是异步的活。

---

## 二、核心难点：提示词长度限制

这是配置 AI 任务时**第一个会撞上的墙**。

云端任务的输入框有长度上限，**实测约 1,455 字符**。超过之后会发生什么？

> **静默截断**。不报错，不提示，就是默默少了后面一截。

这个行为很危险——你以为任务配好了，实际上后半段规则根本没进去。

而完整的巡检规则约 **7,600 字符**，是上限的 5 倍多。

---

## 三、解决方案：规则外置

把规则从任务提示词里**搬进数据表**：

```
┌─────────────────────────────────────────┐
│  AI任务注册表                            │
│  ┌───────────────────────────────────┐  │
│  │ 指令全文                           │  │
│  │ （约 7,600 字符的完整巡检规则）      │  │
│  └───────────────────────────────────┘  │
└──────────────────┬──────────────────────┘
                   │ 读取
┌──────────────────▼──────────────────────┐
│  云端任务提示词                          │
│  （约 1,200 字符的元提示词）              │
│  "读注册表的指令全文，按它执行"           │
└─────────────────────────────────────────┘
```

**好处**：

| 好处 | 说明 |
|---|---|
| 不受长度限制 | 规则多长都行 |
| 改规则不用改任务 | 只改数据表，任务提示词永久不动 |
| 可版本化 | 规则本身也成了数据，有历史可查 |
| 单点维护 | 规则只有一份，不会出现"任务里和表里不一致" |

**元提示词示例**：

```
你是家庭维护工作台的巡检执行器。

第 1 步：读取「AI任务注册表」表，取第一条记录的「指令全文」字段。
第 2 步：严格按「指令全文」中的规则执行本轮巡检。
第 3 步：执行结果写回相应数据表。

注意：不要凭经验补充规则，一切以「指令全文」为准。
```

## 四、门控设计

### 问题

一轮完整巡检要读十几张表，开销不小。但**大多数时候确实没什么事**。如果每 6 小时全量跑一次，绝大部分是白跑。

### 方案

AI 的第 0 步只做两次**极廉价的查询**：

```
读「任务请求表」中 状态=待执行 的条数        → 记为 A
读「AI任务注册表」的 上次运行 时间            → 记为 B

if (A == 0 && 距 B 不足 7 天) {
    输出"无待办，退出"
    return;
}
// 否则读指令全文，进入完整巡检
```

### 效果

| 情况 | 步骤数 | 成本 |
|---|---|---|
| 无事（大多数时候） | ~2 步 | 几百 token |
| 有事 | 完整流程 | 正常成本 |

**约 95% 的成本降低**。

### 为什么用"时间差"而不是"每周一"

这个设计是被问出来的：

> "那如果周一完全执行的话，如果改成 1 小时 1 次，那岂不是周一要完全执行 24 次？"

确实如此。原因是**门控判断本身是写操作的触发点**——如果门控条件是"今天是周一"，那周一有 24 个时间点都满足条件，就全量跑 24 次。

改成"距上次运行 ≥ 7 天"就解决了：

- 门控**不写任何数据**，所以判断保持稳定
- 第 1 次跑完后，"上次运行"被更新，接下来 7 天内都不再触发
- 天然幂等，且**与频率解耦**——频率改成 1 小时还是 12 小时，效果都一样

> 这体现了一个重要原则：**判断条件要基于数据状态，不要基于时间点**。

## 五、巡检规则的骨架

完整规则约 7,600 字符，这里说明它的结构，方便你改写自己的版本。

```
【读表纪律】
  - 能用字段投影就只用需要的列
  - 判断类读取改成"只取最近一条"
  - 读之前先想"这张表会不会很大"

【执行纪律】
  - 用给定的命令模板，不要自由发挥
  - 不要为了"确认"而重复读同一张表

【第 0 步 · 门控】
  - 两次廉价查询 → 无事则退出

【第 1 步】读指令全文，确认本轮范围

【第 2 步】按意图路由分发
  2A  任务请求表 → 按"任务类型"路由到具体处理逻辑
  2B  节日准备 → 检查是否进入准备窗口
  2C  采购汇总 → 跨表汇总需购买项

【意图路由】
  路由 ⓪  新增设备 → 检查设备档案，未建档则报告（不自动建）
  路由 ①  新增维护项 → 检查设备是否存在
  路由 ②  查询类 → 读表汇总后回答
  路由 ③  修改类 → 定位记录后更新

【第 3 步 · 防臆断】
  - 链接必须核实过
  - 数据读不到要报错，不许当空
  - 信息缺失要问，不许猜

【第 4 步】回写结果
  - 时间铁规：写北京时间（平台回读字面值，不做时区位移）
  - 禁凑整：用真实分钟数，禁写 10:15/10:20/整点
  - 防重复：写状态标记，不靠记忆

【第 5 步】收尾
  - 更新「上次运行」
  - 任务状态改为已完成
```

## 六、关键规则详解

### 6.1 读表纪律（最贵的教训）

> **一次把整表长文本读回来，会直接导致任务失败。**

**实际事故**：「数据快照」表累积到 **7.7 万字符**时，一次整表读取让连续两轮巡检都失败（00:00 和 06:00）。

修复前我第一反应是"快照表太大"，但这个判断只对了一半。后来通过分析执行记录发现，更多步骤花在了读取工具文档上——**步骤预算耗尽**才是主因。

**规则**：

```
✅ 好：--fields 字段投影，只读需要的列
✅ 好：只取最近一条记录做判断
❌ 坏：整表读取（尤其含长文本字段时）
❌ 坏：为了"确认"重复读同一张表
```

### 6.2 时间铁规

平台按**写入时的字面值**回读，**不做任何时区位移**。

| 会话给的时间 | 应该写什么 |
|---|---|
| GMT+8 的 15:52 | 直接写 `15:52` |
| UTC 的 07:52 | 加 8 小时，写 `15:52` |

**踩过的坑**：把下午 15:52 按 UTC 写入，页面显示成 07:52，差 8 小时。

**修复方向**：不是让页面去补偿，而是**要求写入方一律写北京时间**。页面 `dtLocal()` 只做格式化，绝不换算。

### 6.3 禁凑整

定时任务写时间时：

```
✅ 用会话上下文里的真实分钟数，如 10:14
❌ 写 10:15 / 10:20 / 整点
❌ 写晚于当前时间
❌ 读不到就估算——应该留空
```

### 6.4 防重复靠数据不靠记忆

AI 每次运行都是无状态的。想"记住上次已经做过了"，必须在数据里留痕迹。

**做法**：完成后在记录的备注里写标记。

```
节日表.备注 = "行程已生成 2026-09-21"
```

下一轮读到这行字，就知道跳过。**不要试图让 AI 记住任何事。**

### 6.5 AI 不许猜

三条红线：

| 红线 | 理由 |
|---|---|
| 链接必须核实过 | 曾自创过"售后政策页"当说明书链接 |
| 设备未建档要报告，不许自动建 | 否则会产生一堆脏数据 |
| 数据读不到要报错，不许当空 | 混淆"失败"和"空"会导致误判 |

## 七、配置步骤

### 7.1 建注册表记录

在「AI任务注册表」表里建一条记录：

| 字段 | 内容 |
|---|---|
| 指令全文 | 完整巡检规则（7,600 字符） |
| 上次运行 | 留空（首次运行后会写入） |
| 待执行数 | 留空 |

### 7.2 建定时任务

新建云端自动化任务：

| 项 | 建议值 |
|---|---|
| 名称 | 家庭维护台·信箱巡检 |
| 频率 | 每 6 小时 |
| 提示词 | 元提示词（见下） |

**元提示词**：

```
读取「AI任务注册表」表中「指令全文」字段的内容，严格按其中的规则执行本轮巡检任务。

执行要求：
1. 先做门控判断（详见指令全文第 0 步）
2. 门控通过后，按指令全文执行完整巡检
3. 结果写回相应数据表

不要凭经验补充或修改规则，一切以「指令全文」为准。
```

### 7.3 验证

| # | 检查项 | 预期 |
|---|---|---|
| 1 | 手动跑一次（无待办） | 约 2 步结束，输出"无待办" |
| 2 | 在 AI 页写一条任务 | 任务进入"待执行" |
| 3 | 再跑一次 | 任务变"已完成"，有结果 |
| 4 | 检查「上次运行」 | 被更新为当前时间 |
| 5 | 再跑第三次（刚跑完） | 又走门控快速退出 |

第 5 项验证门控生效。

## 八、故障排查

### 任务报"执行失败"

**排查顺序**：

1. **是不是读了整表长文本**？查「数据快照」表是不是很大
2. **是不是步骤预算耗尽**？分析执行记录，看步骤数
3. **是不是 token 过期**？重新获取
4. **是不是事务失效**？重新开事务

**分析执行记录的方法**：访问页面的执行数据 JSON：

```
https://<静态资源域名>/page/<nodeId>/0/conversation-data.json
```

里面能看到每一步做了什么。**这是我定位失败原因的唯一有效手段**——在拿到它之前，我连续三轮都在猜，猜错了。

### 规则没生效

检查：

1. 「指令全文」字段是否完整（可能被截断）
2. 元提示词是否指向了正确的表
3. 是否有多个注册表记录（AI 读第一条）

### 提示词里的坑

**只能有一对代码围栏**。

规则里如果需要展示代码块，用文字标记代替，例如：

```
# 代码块开始
命令内容
# 代码块结束
```

**原因**：嵌套的 ``` 会导致外层围栏提前闭合，复制时尾部丢失。这个坑踩了 3 次。

自检方法：

```bash
grep -c '^```' 规则文件.md
# 应该输出 2
```

## 九、成本参考

| 场景 | 单次成本 | 说明 |
|---|---|---|
| 门控退出（无事） | 几百 token | 大多数时候 |
| 完整巡检（有事） | 正常成本 | 只在有任务时 |

按 6 小时一次算，一天 4 次。假设 90% 是门控退出，实际开销很低。

> 这个设计的价值不在于省钱本身，而在于**让 AI 的介入变得不需要犹豫**——不用每次跑之前纠结"这值不值得"。

## 十、设计原则总结

配置 AI 任务时，记住这几条：

| # | 原则 | 一句话 |
|---|---|---|
| 1 | **规则外置** | 规则放数据表，不放任务提示词 |
| 2 | **可变的东西放数据表** | 阈值、名单、话术，都别写死 |
| 3 | **状态落到数据里** | 防重复靠写标记，不靠 AI 记忆 |
| 4 | **判断基于数据状态，不基于时间点** | 否则频率一改就失控 |
| 5 | **读表限定范围** | 整表读长文本会直接失败 |
| 6 | **写时间写北京时间** | 平台不做时区位移 |
| 7 | **不许猜** | 链接要核实，缺信息要问 |
| 8 | **失败和空必须区分** | 混淆会导致误判 |
| 9 | **提示词只有一对代码围栏** | 嵌套会截断 |
