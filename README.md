# 家庭维护工作台（Home Maintenance Workbench）

一个跑在云端的**家庭运维中台**：把家里的设备维护、耗材库存、固定费用、节日生日、日常采购这些零散事务，收进一个手机页面 + 一套数据表，再用定时任务的 AI 在后台帮你盯着。

不是又一个待办清单 App。它的核心主张是：**家务这类事，该由数据表记住，由 AI 判断，而不是靠人的脑子记。**

## 它解决什么问题

一个普通家庭要盯的事大致分五类，每类都有各自的"记不住"：

| 场景 | 常见痛点 | 本项目的做法 |
|---|---|---|
| **设备维护** | 新风机滤网该换了、扫地机尘袋没了、净水器滤芯到期——都靠"感觉" | 每条维护项存**周期天数 + 上次维护日期**，页面按 `上次 + 周期 - 今天` 自动算剩余天数并分档标色 |
| **耗材库存** | 滤芯买了几个、放哪了、还剩多少，完全没数 | 维护项带**备件库存**字段；到窗口但库存为 0 的，AI 自动进采购清单 |
| **固定费用** | 采暖费、物业费、车险每年一次，忘了就被催缴甚至滞纳 | 存**缴费周期 + 下次应缴日**，页面提前预警，点一下"已缴"自动推算下一次 |
| **节日生日** | 农历节日、家人生日，提前多久准备礼物、订餐，年年临时抱佛脚 | 节日表带**提前提醒天数**，到窗口自动生成"准备事项"清单 |
| **临时需求** | "帮我把新买的洗地机加进维护清单"——要么自己点半天表单，要么记不住 | **AI 模块**：说一句话写进任务表，云端定时任务读表后直接落库 |

一句话概括：**把"该做的事"从脑子里，搬到一个会自动提醒的数据底座上。**

## 核心设计

整个项目立在三条原则上。这三条不是设计口号，是踩坑之后被迫沉淀下来的。

### ① 可变的东西放数据表，不写死在流程/提示词里

最容易犯的错是把"房间列表""设备清单""家人姓名"硬编码进代码或 AI 提示词。一旦家里换了设备、改了房间名，就要改代码、改提示词、重新部署。

本项目的做法是**字段选项的唯一来源是数据表 schema**：

```js
// 房间下拉框的选项，从维护清单表的 schema 里读，不硬编码
db.getSchema({ databaseId: DB.MAINT }).then(function (schema) {
  (schema.properties || []).forEach(function (f) {
    if ((f.type === 'select' || f.type === 'multi_select') && f.config && f.config.options) {
      MAINT_OPTS[f.name] = f.config.options.map(function (o) { return o.text; });
    }
  });
});
```

同理，**"提前提醒几天""几天算逾期""每轮巡检做什么"** 全部存在数据表里（偏好设置表 + 节日准备表 + AI 任务注册表），改数据即改行为，不用碰代码。

### ② 状态落到数据里，不靠 AI 记忆

AI 每次运行都是无状态的，你不能指望它"记得上次已经处理过了"。所以防重复靠**写标记**，不靠记忆。

例：节日行程生成后，立刻在节日表里写一句备注 `行程已生成 2026-09-21`。下一轮 AI 读表看到这行字，就知道跳过。

```js
// 判重的依据是数据里的一行字，不是 AI 的记忆
var done = String(rec.备注 || '').indexOf('行程已生成') >= 0;
if (done) return;   // 已生成过，本轮不做
```

### ③ 定时判断交 AI，显式意图交界面

分工是明确的：

- **该由 AI 做的**：模糊判断。"这条维护项是不是真的该换了""这个耗材要不要进采购单""节日该准备什么"——这些需要理解上下文，交给 AI。
- **不该由 AI 做的**：确定性计算。剩余天数、库存够不够、费用到期没——这些页面自己算，**绝不经过 AI**。省 token，也不会错。

AI 只在**你主动写了任务**的时候才动手，其余时间它只做廉价的排队检查。

### 附加红线：AI 不许猜

说明书链接只允许填**核实过能打开的真实链接**；设备没建档就报"未建档"让用户决定，**不许自己新建一条**；数据读不到就报错，**不许当空**。

## 功能一览

### 五个主页面

| 页面 | 做什么 |
|---|---|
| **今天** | 聚合视图：到期的维护项、该缴的费用、快用完的日用品、待准备的节日事项、生日/节日横幅祝福 |
| **维护** | 设备维护项列表，按剩余天数排序，支持"已更换 / 延后 / 编辑 / 删除"，可跳转淘宝/京东搜耗材 |
| **台账** | 四个子模块：固定费用、节日与生日、日用品库存、家庭账本（全部走声明式 CRUD） |
| **AI** | 任务投递信箱：写一句话布置任务，看 AI 的返回结果，也可用于提问/查询 |
| **我的** | 家庭成员管理、偏好设置、数据快照备份、JSON 导出、管理员锁 |

### 关键功能细节

- **剩余天数自动分档**：`≤0` 逾期（红）/ `≤7天` 快到期（橙）/ `≤14天` 临近（黄）/ 其余正常。档位不是写死的常量，默认值可改。
- **库存联动采购**：维护项到窗口 + 备件库存 `0` → AI 归入"需购买"；库存 `>0` → 归入"无需购买"。避免买重复。
- **费用自动滚动**：标记"已缴"后，按缴费周期（月/季/半年/年）自动算下次应缴日。
- **生日与节日祝福**：纯前端实现（不消耗 AI）。登录人当天生日或节日当天，页面顶部弹横幅 + 首次进入弹窗，用 `localStorage` 按日期去重，一天只弹一次。数据来源同时兼容"家庭成员表.生日"和"节日表.类型=生日"。
- **快照备份**：一键把所有表的数据打成一条快照记录存进"数据快照"表，保留最近若干条。误删能回滚。
- **成员权限**：选身份进入，游客只读（所有写操作统一过 `canWrite()` 守卫）；管理员需要密码解锁，仅用于防误操作。
- **加载容错**：17 张表分批加载 + 单表重试；失败的会明确显示"**N 张表未加载 · 点重试**"，绝不渲染成"还没有记录"——这两者混淆会让人误以为数据丢了。
- **真实删除可撤销**：删除维护项后弹 Undo 条，几秒内可恢复。

## 技术架构

一句话：**没有后端、没有构建、没有依赖。一个 HTML 文件 + 一个云端数据底座 + 一个定时任务。**

```
┌─────────────────────────────────────────────────────────────┐
│  手机 / 电脑浏览器                                            │
│  ┌───────────────────────────────────────────────────────┐  │
│  │  index.html  （单文件，约 143 KB，含 CSS + JS）         │  │
│  │  ├─ 5 个视图 / 5 个 Tab                                │  │
│  │  ├─ Store：批量分页加载 + 重试                          │  │
│  │  ├─ HUB：声明式 CRUD 配置                              │  │
│  │  └─ 剩余天数 / 库存 / 费用 全部前端计算                  │  │
│  └───────────────────────┬───────────────────────────────┘  │
│                          │ window.__SMART_PAGE__.database    │
└──────────────────────────┼──────────────────────────────────┘
                           │  （平台注入的 SDK）
┌──────────────────────────▼──────────────────────────────────┐
│  资料库数据层（云端数据库，17 张表）                            │
│  维护清单 / 维护日志 / 固定费用 / 节日与生日 / 日用品库存 ...    │
│                                                              │
│  ┌────────────────────────────────────────────────────────┐ │
│  │  AI 任务注册表                                            │ │
│  │  └─ 指令全文字段：存放完整规则（规则外置）                  │ │
│  └────────────────────────────────────────────────────────┘ │
└──────────────────────────▲──────────────────────────────────┘
                           │  读表 / 写表
┌──────────────────────────┴──────────────────────────────────┐
│  云端定时任务（每 6 小时）                                     │
│  第 0 步 门控：读 2 个数 → 没事就退出（约 2 步）                │
│  有事 → 读注册表指令全文 → 按规则执行 → 回写状态                │
└─────────────────────────────────────────────────────────────┘
```

### 为什么不是自建服务器

一个家庭应用，维护一台服务器本身就是新的家务。所以：

- **不需要服务器**：页面是静态 CDN 托管的单文件，数据在云数据库，没有进程要守护。
- **不需要构建**：没有 npm、没有打包器，改完 HTML 直接上传即生效。
- **不需要安装**：手机浏览器打开就用，可以加到主屏当 App。

### 规则外置（重要）

云端任务的输入框有长度上限（实测约 1,455 字符，超出会静默截断）。所以完整的巡检规则（约 7,600 字符）**不放在任务提示词里**，而是存进数据表「AI 任务注册表」的 `指令全文` 字段；任务提示词里只留一段约 1,200 字符的**元提示词**：

> 读取注册表的指令全文，然后按它执行。

这样规则的增删改改数据即可，任务提示词永远不用动。

### 门控：让"没事发生"几乎不花钱

一轮完整巡检要读写十几张表，开销不小。但大多数时候确实没什么事。所以 AI 的第 0 步是**门控**——只做两次极廉价的查询：

```
读「任务请求表」中状态=待执行的条数
读「AI任务注册表」的上次运行时间

if (待执行 == 0 && 距上次运行 < 7天) {
    // 直接结束，约 2 步，不读表、不写表
    return;
}
// 否则进入完整巡检
```

效果：无事发生时一轮只花几百 token，相比全量巡检降了约 95%。

> **为什么是"距上次运行 ≥ 7 天"而不是"每周一全量"**：门控本身不写任何数据，所以"距上次运行"这个判断保持稳定；如果按"每周一"触发，一旦把任务频率调到每小时一次，周一就要全量跑 24 次。用时间差则天然幂等。

```bash
git clone https://github.com/Magic0ZY/home-maintenance-workbench.git
cd home-maintenance-workbench/demo
# 直接用浏览器打开 demo5.html（双击也行）
# Windows: start demo5.html
# macOS:   open demo5.html
```

打开后就是完整的手机版界面，数据是虚构的示例家庭（扫地机器人、新风机、净水机、猫砂……）。所有交互都能点：加维护项、标记已更换、缴费、布置 AI 任务。

页面左下角的同步状态会显示「**离线预览**」——这是页面内置的降级模式：检测不到平台 SDK 时自动进入，只读不写。

**实现原理**（如果你想知道它怎么跑起来的）：

```js
// index.html 里，SDK 拿不到就是 null
var db = (window.__SMART_PAGE__ && window.__SMART_PAGE__.database) || null;

function boot() {
  bind();
  if (!db) {                       // ← 离线分支
    renderSync('off', '离线预览');
    // 只渲染静态框架，不做任何读写
    return;
  }
  // ...正常云端模式
}
```

而 `mock4.js` 在页面主脚本之前执行，往 `window.__SMART_PAGE__` 塞了一个假的 `database` 对象（`query` / `getSchema` / `addRecord` / `updateRecord` / `deleteRecord` / `onUpdated`），数据存在内存里。

> `demo5.html` 就是 `page/index.html` 加上 mock 注入，**两者功能完全一致**（17 张表全功能：维护、费用、节日、日用品、账本、成员、宠物、物品归档、存放位置、设备档案）。演示时页面的表 ID 是占位符，由 `mock4.js` 按同样的占位符提供假数据。

## 部署到自己的环境

本项目依赖 WorkBuddy 的**资料库数据表**和**页面托管**能力。完整部署分四步。

### 前置条件

- 一个 WorkBuddy 账号，并创建一个空间（Space）
- 记下空间 ID（在空间 URL 里）

### 第 1 步：建数据表

主程序用到 17 张表。**完整表名、字段名、字段类型、选项值的对照表**见 [`docs/数据模型.md`](docs/数据模型.md)。

可以**先建 7 张核心表跑起来**，其余按需再加 —— 页面读不到的模块会显示成空，不影响已建模块的使用：

| 表 | 用途 | 是否必需 |
|---|---|---|
| 维护清单 | 设备维护项主表 | ✅ 核心 |
| 维护日志 | 维护操作流水 | ✅ 核心 |
| 固定费用台账 | 周期性缴费 | ✅ 核心 |
| 节日与生日 | 节日/生日提醒 | ✅ 核心 |
| 日用品库存 | 消耗品囤货 | ✅ 核心 |
| 任务请求表 | AI 任务信箱 | ✅ 核心（用 AI 才需要） |
| AI任务注册表 | 存规则全文 | ✅ 核心（用 AI 才需要） |
| 家庭账本 / 家庭成员 / 偏好设置 / 节日准备 / 数据快照 / 宠物档案 / 宠物护理 / 物品归档 / 存放位置 / 设备档案 | 扩展模块 | 按需 |

> ⚠️ 加表之后记得同步更新代码里的 `SNAP_NAMES`（快照备份名单）和 `Store.loadAll` 的加载清单 —— 漏掉会让这张表没有备份。

### 第 2 步：改配置

打开 `page/index.html`，找到顶部的配置块，把 17 个占位符换成你自己的表 ID：

```js
var DB = {
  MAINT: 'YOUR_MAINT_DB_ID',   // ← 换成你的维护清单表 ID
  LOG:   'YOUR_LOG_DB_ID',
  FEE:   'YOUR_FEE_DB_ID',
  FES:   'YOUR_FES_DB_ID',
  DLY:   'YOUR_DLY_DB_ID',
  TSK:   'YOUR_TSK_DB_ID',
  REG:   'YOUR_REG_DB_ID',
  // ...其余 10 个同理（LEDGER / MEMBER / PREF / PREP / SNAP / LOC / PET / PETCARE / ITEM / DEV）
};
```

> 只建了 7 张表的话，把另外 10 个留空即可 —— 页面容错，不会崩。

字段名常量 `MF` 也要与你的表字段一一对应（如果你照搬推荐 schema，则不用改）。

### 第 3 步：上传页面

页面通过"事务"方式上传：

1. `create_page_transaction` —— 开一个页面事务，拿到事务 ID
2. `get_page_upload_url` —— 拿上传地址
3. PUT 上传改好的 index.html
4. `commit_page_transaction` —— 提交，生成新版本

> ⚠️ **事务有时效**。开了事务之后如果隔太久才 commit，会报 `transaction not found`——重新开一个事务再传即可。

静态资源地址形如：

```
https://workbuddy-space-static.codebuddy.work/page/<nodeId>/<version>/index.html
```

### 第 4 步：配定时任务（可选，用 AI 功能才需要）

1. 在资料库建一条「AI任务注册表」记录，把完整巡检规则写进 `指令全文` 字段（规则正文见 [`docs/AI任务配置.md`](docs/AI任务配置.md)）
2. 新建一个云端自动化任务，频率设为你需要的间隔（推荐 6 小时）
3. 任务提示词里粘贴那段约 1,200 字符的**元提示词**（不是完整规则）：
   ```
   读取「AI任务注册表」中指令全文字段，按其中的规则执行本轮巡检。
   ```
4. 跑通一轮，确认能正常读写

```
                      │  家庭成员     │
                      └──────┬───────┘
```

| 房间 | select | 选项来自 schema（唯一来源） |
| 类别 | select | 米家电器 / 宠物设备 / 清洁设备 ... |
| 维护动作 | select | 清洗 / 更换滤网 / 更换耗材 / 更换电池 / 深度保养 |
| **周期天数** | number | 计算剩余天数的基准 |
| **上次维护日期** | date | 计算剩余天数的基准 |
| 耗材型号 | text | 用于生成购买搜索链接 |
| **备件库存** | number | 是否为 0 决定要不要买 |
| 耗材单价 | currency | 采购清单估算金额 |
| 说明书链接 | url | **只允许填核实过的真实链接** |
| 说明书图片 | image | 存档 |
| 备注 | text | 也用于写状态标记（"行程已生成 xxx"） |

**保存字段值的格式**（写 API 时最容易踩的坑）：

```js
// 保存时的格式：单键扁平映射
{ '维护项': { text: '尘袋' },
  '周期天数': { number: 60 },
  '上次维护日期': { date: '2026-09-01' },
  '备件库存': { number: 0 } }
```

**读回来的格式则不一样**，这是本项目最需要小心的地方：

| 字段类型 | API 回传形态 | 页面取值 |
|---|---|---|
| text / select | 字符串 | 直接用 |
| number / currency | 数字 或 `{amount}` | `numOf()` |
| date | `"2026-09-17T00:00:00Z"` | `parseDay()` |
| **multi_select** | **数组**（元素可能是对象，取 `.text`） | `toArr()` |
| **url** | **数组 `[{link, text}]`** | `valLink()` / `valLabel()` |
| **image** | **数组 `[{imageUrl}]`** | `imgUrlOf()` |
| checkbox | 布尔 | 直接判断 |

> **铁律**：渲染链接/图片一律走 `valLink()` / `imgUrlOf()` 转换，**绝不**把原值直接拼进 `href` / `src`。踩过的坑：url 字段直接拼进 `href`，渲染成了 `[object Object]`，浏览器按相对路径解析，报 `NoSuchKey`。

## 已知限制

诚实说明，避免误解：

1. **强依赖平台**。数据读写走的是平台注入的 SDK，脱离该平台**无法连接真实数据**。离线演示只是界面预览，数据不落盘。
2. **前端密码不是安全边界**。管理员锁只是防误操作和手滑；真正的防线是**数据表分享权限**——给家人开"查看"而非"编辑"。
3. **没有实时推送**。所有提醒都是"打开页面才看到"。真正需要主动触达的场景（比如老人忘了吃药）覆盖不到。
4. **AI 判断存在不确定性**。规则里已经明确要求"不许猜、不许自建数据"，但仍需人工抽查。
5. **单文件有维护上限**。目前主程序约 2,440 行、10.6 万字符，仍可读但已接近单文件舒适区，继续加功能需要考虑拆分。
6. **无自动化测试**。验证靠代码走查 + 数据核对 + 手工回归。

## 未来升级方向

按"投入产出比 × 可行性"排序：

### 近期（低成本、明确有价值）

- **PWA 化 + 主屏图标**：加一个 `manifest.json` 和 Service Worker，手机加到主屏后离线也能看缓存数据，体验接近原生 App。
- **最低库存告警**：现在是"库存为 0 才告警"，可以借鉴 Grocy 的做法，支持为每种耗材设安全库存线，低于线就提醒。
- **多成员消息推送**：目前提醒只在页面内。可接入企业微信/钉钉机器人，把"今天该换滤网"推到群里。
- **位置层级化**：目前"存放位置"是单层（客厅/厨房）。可借鉴 HomeBox 的 `房间 → 柜子 → 层板` 三级模型，找东西更准。

### 中期（需要额外开发量）

- **扫码录入**：给物品贴二维码，扫码直接跳到该物品详情页；新购耗材扫码入库。HomeBox 已经验证过这个交互。
- **米家 / Home Assistant 接入**：如果设备能上报状态（滤芯寿命、耗电量），就能把"按周期估算"升级为"按实际使用量计算"，更准。目前因平台未开放接入而搁置。
- **数据可视化**：家庭支出的月度/年度趋势、维护频次热力图、耗材消耗速度曲线。
- **多家庭/多房产支持**：现在一套表对应一套房子。若管理多套房，需要加"房产"维度。

### 远期（方向性探索）

- **图片识别录入**：拍一张耗材包装，OCR 识别型号和规格自动填表。
- **语音录入**：说"洗衣机筒清洁做完了"，直接落库。
- **自托管版本**：把数据层从云数据库换成 SQLite/Postgres，整套跑在自己的 NAS 上。**触发条件**：如果平台依赖成为实际障碍，或者需要完全的数据主权，再走这条路。目前不迁移的理由是——自托管会让"维护一个家庭应用"本身变成新的家务。

### 明确不做

- ❌ **做成通用 SaaS**。这个项目的价值恰恰在于它是**为自己家定制的**：房间名、设备清单、家人的习惯，这些恰恰是通用产品做不好的部分。
- ❌ **堆砌功能**。每加一个模块都要先问：它是不是真的能减少一次"记不住"？

## 设计原则（踩坑总结）

项目在迭代中沉淀了这些规则。如果你要改代码，强烈建议先读完——**每一条都是真踩过的坑**。

| # | 原则 | 背后的坑 |
|---|---|---|
| 1 | 字段选项的唯一来源是数据表 schema | 硬编码房间名，改一次要动多处代码 |
| 2 | **静态 `fields` 不能引用动态数据** | 配置里 `fields` 写成数组字面量时，`roomList()` 这类函数会在模块加载时求值为**空**。凡是 options 来自数据，必须写成 `fields: function () { return [...]; }` |
| 3 | 改 select 选项前先查该表有没有数据 | 删选项会**静默清空**引用它的单元格 |
| 4 | 状态落到数据里 | 防重复靠写标记，不靠 AI 记忆 |
| 5 | 可变的东西放数据表 | 写死在流程里 = 每次改都要重新部署 |
| 6 | **写操作统一过 `canWrite()`** | 新增写入口忘了加守卫，游客就能改数据 |
| 7 | **加表要同步更新快照名单 `SNAP_NAMES`** | 漏掉等于这张表没有备份 |
| 8 | 前端密码不是安全边界 | 真防线是数据表分享权限 |
| 9 | 加载要容错，失败 != 空 | 渲染成"还没有记录"会让人以为数据丢了；必须显示"没加载上（不是数据没了）" |
| 10 | 核查数据时区分 ERROR 与空 | 用 `.get('results', [])` 会把失败读成 0 条 |
| 11 | 页面事务有时效 | 事务开太久才 commit 会报 `transaction not found` |
| 12 | **表单默认值只能补空，不能覆盖** | `cfg.defaults()` 曾无条件覆盖用户刚填的值（把用户选的日期改成今天）。正确写法：`if (dft) for (var k in dft) { if (!props[k]) props[k] = dft[k]; }` |
| 13 | **写日期时间一律写北京时间** | 平台按**写入时的字面值**回读，不做时区位移。页面 `dtLocal()` 只格式化不换算 |
| 14 | 定时任务写时间禁凑整 | 用会话上下文里的真实分钟数，禁写整点，禁写晚于当前时间 |
| 15 | **渲染链接/图片一律过 `valLink()` / `imgUrlOf()`** | 直接拼进 `href` 会渲染成 `[object Object]` |
| 16 | 读表必须限定范围 | 一次把整表长文本读回会**直接导致任务失败**（曾因 7.7 万字符的整表读取连续两轮巡检失败）。能用字段投影就只用需要的列 |
| 17 | 提示词里只留**一对**代码围栏 | 嵌套围栏会导致复制时尾部丢失 |
